# 待确认问题与悬置决策

分两类：**A. 需要向主办方/平台确认的外部问题**（我们无法自行得知），**B. 我们自己刻意悬置的内部决策**（需要实测数据才能定）。

优先级标注：🔴 阻塞（不确认会导致设计错误或分数直接损失）、🟡 高（影响策略与体积）、🟢 中（影响交付细节）。

---

## A. 需要向主办方 / 平台确认

### A1. 时间预算

| # | 优先级 | 问题 | 为什么重要 |
|---|---|---|---|
| 1 | 🔴 | **跑分任务的总时限是多久？** 有没有接口或响应字段能读到 deadline？ | `GET /challenges` 的响应里**没有任何时限字段**。编排器的两阶段预算、时间片分配、收尾保护全部依赖这个值。读不到就只能靠环境变量手填保守值，填错要么浪费时间要么收尾不完 |
| 2 | 🔴 | 任务超时后，已启动的容器是平台自动回收，还是仍需选手显式 `close`？ | 决定收尾保护是否必须包含 close 全量容器，以及超时后 close 会不会返回 `invalid_state` 而污染错误处理 |

### A2. 网络与沙箱能力

| # | 优先级 | 问题 | 为什么重要 |
|---|---|---|---|
| 3 | 🔴 | **托管沙箱的靶场可达性由谁提供？** 平台是否已在网络层打通（容器直接能连 `container_addr`），还是需要容器内自拨 `ing/*.ovpn`？ | 托管模式明确无公网，而 VPN 端点是**公网地址**（值见 `ing/` 原件，公开仓库中不写） —— 若需自拨而沙箱掐公网，则根本拨不出去，整个 Agent 无法访问任何靶场，直接零分。当前设计按「平台已打通」推定，并保留自拨分支 |
| 4 | 🔴 | 沙箱是否授予 `CAP_NET_ADMIN`、`/dev/net/tun`、`CAP_NET_RAW`？ | 前三者决定能否自拨 VPN；`CAP_NET_RAW` 决定 nmap `-sS` 半开扫描、masscan、tcpdump 能否使用。无 raw socket 时扫描能力大幅下降（只能退化为 TCP connect 扫描，慢且易被目标日志记录） |
| 5 | 🟡 | 除大模型网关与 `BENCHMARK_BASE_URL`，沙箱还能访问什么？靶场网段之外是否有其他白名单？ | 决定哪些工具需要完全离线化，以及能否访问外部资源辅助解题 |
| 6 | 🟡 | 大模型网关是否有速率限制、并发限制、token 配额？**平台答题 API 本身是否限频？** | 3 题并发 × 长 agent 会话可能撞限流。若有配额，需要在编排器层做全局限速，而不是让 solver 各自撞墙。**具体化假设**：第二届 API 文档明确规定「每队每秒最多 3 次接口调用，所有接口共享计数，超出返回 429」。本届文档对此**只字未提**。编排器已按 ≤3 req/s 自我限速（[architecture.md](architecture.md) §5.1），若本届确无限频则无害 |
| 7 | 🟡 | **网关是否支持流式（SSE）响应？是否完整透传 DeepSeek 的 tool-calling / function-calling？** | 几乎所有 agent 框架默认流式 + 强依赖 function calling。网关若做了协议裁剪（不透传 `tools` 字段或不支持 SSE），内层框架选型会被直接推翻 —— 这必须在选定框架之前验证 |
| 8 | 🟢 | 沙箱的磁盘配额、进程数（pids）限制是多少？ | solver 会产出大量文件、并 fork 出 sqlmap/ffuf 等并发子进程。撞 pids 限制会表现为「工具莫名启动失败」，很难现场定位 |
| **18** | 🟡 | **平台是否也直接下发一个「生成好的大模型网关地址」，还是坚持让我们按规则手拼 `.tsecbench.gw`？此外本届是否还提供 MCP 接入端点？** | 第二届的做法是**直接给你一个网关 URL**（其 MCP 文档原文：`MODEL_URL = "<LLM_GATEWAY_URL>" # 您生成的大模型网关地址`），且**同时提供 HTTP API 与 MCP 两种接入**（5 个工具）。本届改成下发改写规则让我们自己拼。**若本届页面上其实也有现成网关地址，我们手拼就有出错风险**，而这是单点风险最高的 20 行代码（见 [architecture.md](architecture.md) §6.2）。若有 MCP 端点可用，也能省掉自写 REST client |
| **19** | 🔴 | **本届是否存在关卡（level）解锁门？对应 `403` 错误码与解锁提示语义？** | 上届明确有：响应含 `current_level`，`403 = 比赛尚未开始 / 尚未解锁对应关卡`，提交正确后 `message` 追加 `【您已成功解锁新的关卡】`。本届响应里**有 `level` 字段但无 `current_level`，错误码表里也完全没有 403**。CHYing-agent 的上届复盘佐证卡关是真实机制（全程 54 flag 解出 30 个，「卡在了第三关」）。**若本届有而我们不处理**，Phase 1 会把 3 个并发额度全占在高关卡题上反复撞墙，白烧预算与限频配额。编排器已先写好 `LOCKED` 状态分支（无关卡门时永不触发，零成本） |

| # | 优先级 | 问题 | 为什么重要 |
|---|---|---|---|
| 9 | 🔴 | **初赛题集的题型分布与题目数量？** 是否包含内网横向 / 多机靶场？ | 决定工具链怎么裁剪、体积预算怎么分。`container_addr` 是数组且文档提到「一个题目可能有多个地址」，这可能意味着多机内网题 —— 若真有，需要额外准备横向移动工具（代理转发、内网扫描、凭据复用），当前清单未覆盖。**已有可参考量级**：第二届主赛**共 54 个 flag**（CHYing-agent 复盘数据），若本届量级相近，Phase 1 的每题时间片就能反推出来。<br>**另需明确：题集里是否有 Windows 主机目标？** 这决定后渗透工具链要不要做（当前判定为不做，理由见 architecture.md §11.3）|
| 10 | ✅ 已决 | **`hint_cost_radio` 能否在 `GET /challenges` 响应里读到？** | 文档缺口确认：§2 说「具体比例由题目配置决定」，但响应字段里**没有**。**决策：不取 hint，缺口不再需要回答** —— 成本不可知（无法盲决策）+ 实测 10 次仅 1 次换出解出（期望收益为负），整条 hint 链路已删除，见 [architecture.md](architecture.md) §4.4、[platform-api.md](platform-api.md) §4.7 |
| 10b | ✅ 已决 | **本届响应为何没有 `hint_viewed`？** 上届有。 | 该缺口曾是崩溃恢复路径上唯一不可对账的状态（需 Journal fsync 兜底）。**决策：不取 hint → 本地不再持有读不回来的状态，缺口随之消失**，Journal 也不再需要同步落盘事件。见 [architecture.md](architecture.md) §4.4 |
| 11 | 🟡 | **错误提交 flag 是否有次数限制或惩罚？** | 文档只说正确提交幂等（`duplicate`），未提错误提交的后果。若无限制，可以对正则收割出的全部候选无脑批量提交，大幅提高命中率；若有惩罚（扣分/封禁），必须保守只提交高置信候选。这一条直接改变 Flag Harvester 的策略 |
| 12 | 🟢 | `POST /start` 的并发上限 3，是否把 `pending` / `stop_pending` 状态也计入活跃？ | 影响并发闸门的计数口径。若 `stop_pending` 也计数，close 之后需要等状态真正变 `stopped` 才能 start 新题，否则撞 409 |
| 13 | 🟢 | 对 `pending` 状态的容器调用 `close` 是否允许？`stop_pending` 期间重复 `close` 返回什么？ | 决定 close 的重试与容错写法 |
| **20** | 🟡 | **「云攻击」能力域的靶场形态是什么？**（K8s / 编排 API？容器逃逸？云元数据与 STS 凭据（SSRF→IMDS）？）以及「多阶段渗透」域是单机多步还是多机横向？ | 旗舰集口径含这两域（[architecture.md](architecture.md) §13.2）→ 决定 B14（云 / 横向最小工具面）；A9 的「是否多机」子问题并入本问 |

### A4. 镜像与交付

| # | 优先级 | 问题 | 为什么重要 |
|---|---|---|---|
| 14 | **🔴（原 🟡，因体积重算而升级）** | **3GB 上限指的是上传文件（压缩后 tar.gz）大小，还是解压后的镜像大小？** | **这一条现在直接决定 Ghidra + REA 能不能留。** 文档写「支持 .tar/.tar.gz/.tgz，最大 3GB」，语义上指上传文件大小，但需要确认。当前预算（2026-10-10 重算，含 Ghidra+JDK+REA+Go recorder）为**压缩后 ~1.88GB**：若按压缩口径，余量 1.12GB，安全；若按**解压后**口径，压缩比 2.5~3× 意味着解压约 4.7~5.6GB，**直接超标**。为此已备好按「解压 ≤3GB」严口径裁剪的降级阶梯（[image-spec.md](image-spec.md) §4.1，第 3+4 步一起砍 Ghidra+REA 可省 ~600MB）。**在答复之前不要开始写 Dockerfile** —— 否则可能整个工具链布局要返工 |

## B. 内部悬置决策

这些是刻意推迟的，需要实测数据才能定，现在拍板是浪费。

| # | 决策 | 触发条件 / 判据 |
|---|---|---|
| B1 | **内层执行体：~~择一现成框架~~ → 已定为「读源码 + 自研薄壳」（2026-10-10）** | 决策已下：**全部 clone 到 `refs/` 读完源码，自研薄壳，不整体移植任何框架**。理由（每条都是硬阻塞，见 [architecture.md](architecture.md) §2.5）：ctf-agent 要 `aiodocker`（沙箱内无 DinD）+ `claude-agent-sdk`（我们只有 DeepSeek）；BreachWeave 是 Bun+TS+pi-mono 且为人机协同设计；ARTEX 是 AGPL-3.0 + 强制 PostgreSQL + **原仓库已从 GitHub 下架**；ARTEMIS 依赖 vendored Codex Rust 运行时。**但自研范围有严格边界，防止膨胀成重写框架**：只做 ① Adapter 薄壳 ② 工具调用的进程隔离与超时 ③ 双图状态的最小 JSON 实现；**LLM 循环本身用现成库（openai SDK 直连 DeepSeek），不自己写**。<br>**仍需实测的部分**：薄壳在 DeepSeek 下的单题收敛率。若明显低于现成框架，`xbow-competition` 那条「薄壳包现成 CLI」的路要重新考虑 —— 它已验证可行（第一届初赛 7/238）。<br>**评测基线**：`BoxPwnr`（`0ca/BoxPwnr`，Python ≥3.10，支持 HackTheBox / TryHackMe / PortSwigger / Cybench / picoCTF）可作为**不依赖真 token 的离线解题基准**，让我们在手上有 token 之前就能测薄壳的解题能力 —— 这一点价值很高，此前没想到 |

| **B11** | **Lua 的三条用途里，哪几条真做** | 已在 [architecture.md](architecture.md) §1.5 定位（宿主侧嵌入方案已在 §1.5.1 驳回）：① NSE 自定义探测脚本 ② 面向 Redis/OpenResty 类目标的 Lua 代码执行 ③ 薄壳内轻量插件点。**①②做，③默认不做**（投机设计）。<br>**待实测确认的是①的实际价值**：让 LLM 现写 NSE 脚本，能不能真写出可运行的？NSE 的标准库（`nmap.new_try`、`stdnse.get_script_args`、`shortport.*`）对模型是陌生的，写出语法正确 + 语义可跑的脚本，成功率可能远低于写 Python。若实测发现写不出，**就把①降级为「只用现成的 612 个脚本 + 参数化调用」** —— 这仍然有价值，且不依赖模型会写 Lua。<br>**红线（现在就定死，不留到赛中）**：镜像内不预置任何针对特定题目的 `.nse` 或 Lua payload。允许内置通用能力，不允许内置题解 —— 与 §10.4 同源 |

| **B13** | **是否在 Go `recorder` 里嵌 `gopher-lua` 做请求阶段规则** | 这是外部建议中**唯一被承认有未来的宿主侧 Lua 用法**（`yuin/gopher-lua` ★6988，事实标准，零 CGO；Kong / Envoy / Mosquitto 都正是这么嵌 Lua 的）。<br>**现在不做**：§1.2 把 recorder 定义为「只做录制 + 去重 + 重放，不做脚本化改写」，加 VM 就加崩溃面。<br>**明确的触发条件**（只有出现才算数，不是「因为能做所以做」）：需要**按流量特征自动触发响应动作** —— 例如「录到 302 且 Set-Cookie 含 session 就自动重放上一组 payload」。在此之前手写 Python 分支即可。<br>其余宿主侧 Lua 方案（Python 经 Lupa 嵌 LuaJIT、Rust 经 mlua 暴露扫描函数、Redis Lua 原子锁协调 worker）**已全部驳回**，理由见 [architecture.md](architecture.md) §1.5.1 与 §11.2 —— 注意 Redis 那条的前提（我们有自己的 Redis 做跨机协调）在本项目的单容器无公网沙箱里根本不存在 |
