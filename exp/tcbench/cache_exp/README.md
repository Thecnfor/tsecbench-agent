# DeepSeek 前缀缓存 × fork 交叉对话 实验

**结论（2026-10-15，deepseek-flash，40 请求 / ~915k prompt tokens / ≈$0.04）**：
多 agent fork 交错推进（a1 b1 a2 a3 b2）**缓存上几乎零代价**——逐请求命中率与顺序执行完全一致；
跨分支共享前缀成立（B 分支首请求 99.2% 命中 A 写入的前缀）。三个真实风险与对策见下表。

## 方法

`run.mjs`（零依赖 Node 脚本，独立于 tsec_agent）：合成消息（system 500 + 共享上下文 1800
+ 分支指令 + 若干轮，实际每请求 ≈21k prompt tokens），temperature 0、输出 ≤16 tok，
每请求间隔 3s，每条件 2 重复、salt 隔离防跨条件污染，读返回
`usage.prompt_cache_hit_tokens / prompt_cache_miss_tokens`。

- 运行：`node run.mjs`（全条件）/ `EXP_CONDS=E,F node run.mjs`（补跑指定条件）
- 护栏：`maxRequests=70`、`maxPromptTokens=500000`（第一轮在 E 触发过一次，属预期生效）
- key 走 `../.env` 的真实 `DEEPSEEK_API_KEY`（flash off-peak：miss $0.15/M、hit $0.003/M）

## 结果

热身后（首轮冷启动除外）所有正常路径逐轮稳定在 **94.9%–95.9%** 命中。

| 条件 | 总命中率 | 关键读数 | 设计含义 |
|---|---|---|---|
| A 单线顺序 6 轮 | 81.3% | 热身 95%+ | 基线 |
| B fork 后顺序（A 3 轮→B 3 轮） | 80.5% | **b1 = 99.2%**（miss 仅 180 tok） | fork 本身近似免费；共享前缀跨分支命中 |
| C 交叉 a1 b1 a2 a3 b2 | 77.5% | **逐请求与 B 完全相同** | **交错轮转不掉缓存**（总率差只是冷启动权重） |
| D B 分支改写 system | 62.6% | b1 = **21.8%** → b2 自愈 94.9% | 代价一次性、单分支自愈；但红线：分支指令只 append，不动 system |
| E 交叉+中途插入合并（近尾部） | 77.2% | m1 = 92.5% → m2 = 95.2% | 插入代价 ∝ 分叉点深度；合并走尾部追加即便宜 |
| F a1/b1 并发首发 | 48.7% | **双双 0% 命中**（共享段都没读到） | 每分支首个请求要串行，之后随便并发 |

## 对 fork 多 agent 设计的红线（已验证）

1. **交错调度 a1 b1 a2 a3 b2 免费**——分支调度器无需为缓存做任何妥协；
2. **分支指令 append 在共享前缀之后，绝不改写 system**（D 实测 21.8%，虽自愈但没必要付）；
3. **合并/注入只做尾部追加**——缓存按「第一个分歧 token 起全 miss」计费（E 实测近尾插入 92.5%，
   深处插入会线性恶化）；分支摘要注入对方尾部即可；
4. **分支首请求串行**（a1 完成再发 b1），避免共享前缀双冷启动（F 实测双 0%）；首跳之后
   并发/交错随意；
5. N 个分支的冷启动成本 ≈ 1 个分支（共享段只冷一次）。

## 已知局限

- 合成消息只验证缓存机制，不验证解题质量/分支策略收益；
- E 的插入点在历史近尾部（≈2k tok 处）；把 B 的**整段历史**插进 A 中段会深分叉、代价更高——
  这正是「合并只走尾部」红线的另一个理由；
- 闲置淘汰（缓存保留数小时~数天）未测：真实调度分支间隔是秒~分钟级，不构成风险；
- hosted 转写网关是否透传 cache 字段未验证（本地官方 API 实测有）。
