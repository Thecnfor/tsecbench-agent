# Payload DB — 内存安全（TCP 行协议服务 / 二进制）

> 这类题的服务多半是「纯文本命令 + 行协议」，flag 在服务进程内存里。
> **先交互摸协议，再谈利用** —— 不要在没跑通协议前就上 fuzzer。

## 0. 起手（60 秒内做完）
- 连上先读 banner，发 `help` / `?` / 空行看命令表。
- 逐条命令试正常路径，记下**回显格式**（哪部分是我们可控、哪部分是服务数据）。
- 若有二进制：`file`、`checksec --file=`、`strings -n6 | grep -iE 'flag|/flag'`、
  `nm -C`（未 strip 时直接看函数名）。
- **先找「谁把用户长度当成了服务数据长度」** —— 行协议内存 bug 九成是这个。

## 1. 越界读（Heartbleed 式）——f1-03 这类
- 症状：一条命令**声明一个长度**，服务**按该长度回吐数据**，而不校验实际载荷长度。
- 攻击：声明长度 >> 实际载荷 → 回吐相邻内存（含 flag）。
- 手法：`SET <data>` 后再用**大的请求长度**查询；或直接构造 `CMD <huge_len>` 不带足量数据。
- 变体：长度字段与载荷长度分属两条命令时，**第二条的长度不校验**。
- 扫描长度：从正常长度开始逐档放大（100,200,256,257,512,1024,4096），
  **看回吐里非零字节的位置** —— 非零区就是泄露的内存。
- 若回吐里没有明显 flag：把泄露的原始字节 `strings` 一遍或 hexdump 找 `flag{`。

## 2. 越界写 / 堆破坏（token store / LRU cache 这类）
- 症状：固定大小缓冲区 + 用户可控长度拷贝（`strcpy`/`memcpy`/`read` 不校验）。
- 攻击路径：超长键/值 → 覆写相邻结构（长度字段、指针、或**下一条记录的标志位**）。
- 先确定**布局**：连续插入带标记的条目，再用越界写去改某条目的长度/指针，
  观察哪条命令的输出变了 → 反推相邻关系。
- 目标不一定是 RCE：**改长度字段让下一次读越界**，往往比造 shell 更快拿到 flag。
- LRU 淘汰逻辑常有 bug：淘汰后**不清理**或**重复释放** → 读已释放槽位得到旧内容（含 flag）。

## 3. 协议级逻辑洞（不用内存破坏）
- 索引越界：`GET -1`、`GET 999999`、`LIST` 后按返回索引取。
- 类型混淆：数字当字符串、字符串当数字（`len` 字段与 `str` 字段互换）。
- 编码/转义不一致：`\x00` 截断、多字节长度与实际字节数不符。
- 竞态：并发两条命令让「校验」与「使用」之间状态被改。
- **这些常常比内存破坏更快**：先花 2 分钟试逻辑洞，再进内存破坏。

## 4. 利用纪律
- 每一步**只改一个变量**，记录命令 → 回显 → 结论（写进 /root/notes.md）。
- 拿到任何疑似 flag 就**立刻** `echo 'FLAG{...}'` 打到 stdout 或写 `out/flags/`，
  不要等「确认无误」—— 编排器会实时收割（被超时杀掉时已产出的候选仍有效）。
- 无 pwntools 时用纯 socket + `struct.pack` 手搓（镜像可能没装 pwntools）。
